Section 1

What happens when 1,000 tasks
fight for the same memory?

A data center runs hundreds of workloads simultaneously. Each task needs memory, but fast DRAM is limited. When too many tasks get routed to the same memory tier, everything slows down. Watch it happen in real time.

Normal load: 8 tasks
A small cluster with 8 tasks. Classical scheduling (FCFS: first come, first served) assigns them in arrival order. DRAM fills up, remaining tasks go to CXL. Everything works fine. Latency is manageable.
Scale to 100 tasks
Now DRAM is overwhelmed. FCFS has no intelligence, meaning it doesn't know which tasks are memory-sensitive. High-priority tasks get stuck on slow CXL. The red lines appear: congestion, wasted cycles, SLA violations.
Scale to 1,000 tasks
At this scale, even smart greedy heuristics break. There are 2¹⁰⁰⁰ possible assignments, representing more combinations than atoms in the universe. Classical algorithms can only sample a tiny fraction. The data center is gridlocked.
Quantum: all green lanes
RQAOA encodes every task into a quantum state. Through superposition, it explores all possible memory assignments simultaneously. The result: an optimised assignment where sensitive tasks get DRAM and insensitive tasks gracefully use CXL. All green.

Superposition Demo

Path exploration in a maze

A classic optimization problem: finding the exit of a maze. Observe how a classical algorithm must sequentially search each route, while a quantum system searches all options at once.

Classical (Sequential) Search
Testing Path 1 of 4...
Classical algorithms (like DFS/BFS) trace paths one-by-one. When they hit a dead end, they must backtrack and try the next route sequentially.
Quantum (Parallel) Search
Exploring all 4 paths...
Quantum algorithms represent all paths in superposition. They explore all routes simultaneously, and use interference to cancel out dead ends.
Why does this matter for scheduling?
With 8 tasks, there are 2⁸ = 256 possible DRAM/CXL assignments. A classical computer tries them one at a time. A quantum computer, using qubits, represents all 256 states simultaneously and finds the best one through interference, amplifying good solutions and cancelling bad ones. That's what RQAOA does.

Section 3

System architecture: step by step

This is exactly how the system is built. Each stage feeds the next. Click through to see the data flow from a CLI command to optimised results.

Step 1 of 6
main.py
CLI entry point

The user runs python main.py --scheduler rqaoa. This parses the scheduler flag and passes control to the benchmark orchestrator. Supports: fcfs, rr, greedy, greedy_priority, rqaoa, or all.

Challenge we solved: Getting a single entry point to work across both classical and quantum paths required designing a clean scheduler interface (BaseScheduler) that all 5 algorithms implement identically, so the orchestrator doesn't care which one it's running.
run_benchmarks.py
Benchmark orchestrator

Loads the canonical 8-task set from tasks.py, runs each selected scheduler, collects assignments, then hands each assignment to the execution layer. This is the central control loop of the entire system.

Design decision: We separated "scheduling" from "execution". The schedulers only produce a {'{'}task_id: "DRAM" | "CXL"{'}'} dict. They never touch subprocesses. This made the system modular and testable: you can unit-test schedulers without launching any real processes.
Classical Schedulers
FCFS · Round Robin · Greedy · Priority

Four classical baselines, each taking a different approach: arrival order (FCFS), alternating assignment (Round Robin), sensitivity-sorted (Greedy), and priority × sensitivity composite (Priority-Weighted). All output the same {'{'}task_id: "DRAM" | "CXL"{'}'} dict format.

Key insight: Even the best classical scheduler (Greedy) only considers one dimension at a time. It can't jointly optimise memory sensitivity, priority, and capacity constraints simultaneously, which is where QUBO shines.
Quantum (RQAOA)
qubo_builder → qubo_converter → rqaoa_runner → result_parser

The quantum path: First, qubo_builder.py constructs an 8×8 cost matrix encoding latency penalties and DRAM capacity constraints. rqaoa_runner.py feeds this to the RQAOA optimizer (via OpenQAOA on the Qiskit Aer simulator). The output bitstring is decoded by result_parser.py into the same assignment dict.

Challenge we solved: OpenQAOA and our QUBO builder use different matrix formats. We built qubo_converter.py to translate between them, which is a deceptively tricky format-bridging step that had to preserve coefficient signs exactly, or the optimizer would minimise the wrong objective.
Execution Layer
task_orchestrator.py · task_runner.py

Takes each scheduler's assignment dict and launches real OS subprocesses. Each task runner allocates memory, performs work, and simulates the CXL 3× latency penalty via calibrated time.sleep() calls. DRAM tasks run at baseline speed; CXL tasks are visibly slower.

Challenge we solved: AWS EC2 doesn't support numactl NUMA-faking (CONFIG_NUMA_EMU is not compiled into Ubuntu kernels). We pivoted to software-level latency simulation inside task_runner.py, injecting precise per-access delays to replicate the 3× CXL penalty faithfully. This decision is documented in docs/numa_verification.md.
Evaluation
metrics.py · graphs.py → results/

Computes average completion time, makespan, total latency cost, and DRAM utilisation for each scheduler. Generates comparative bar charts and saves everything to results/ as CSVs and PNGs.

Output: all_schedulers_summary.csv with one row per scheduler, and execution_log.csv with one row per task. Four publication-ready plots comparing all five scheduling strategies.
